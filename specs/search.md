# Спецификация: поиск

Как PetTemplate ищет по смыслу и по словам: эмбеддер,
векторный индекс в Qdrant, полнотекстовая половина в PostgreSQL, слияние, реиндекс
и изоляция пространств. Справка ищется в памяти тем же эмбеддером и тем же слиянием
(`help.md`, 6); ассистент ходит в неё инструментом `search_help` (`assistant.md`, 7).
Инструментов поиска по сущностям у ассистента в ядре нет — сущностей нет.

> **Статус — действует.** **Только механизм:** сущностей с текстом в шаблоне нет,
> `SearchEntityType` пустой (`None`), эндпоинта поиска и экрана с ним нет. Раздел проекта
> подключает поиск к своей сущности по рецепту из раздела 9; проверяется механизм на
> тестовой сущности тестового проекта (`tests/…/Features/Search/TestNotes`).

## 1. Зачем

Список фильтруется по полям, но не по смыслу. «Где было про отчёт для бухгалтерии» точным
фильтром не решить: в записи могло быть написано «акт сверки для финансового отдела». Слова
в запросе и в записи разные — поиск по подстроке не найдёт.

Разделение не по тому, что лежит в индексе, а по тому, чем отвечать:

| Вопрос | Чем отвечаем |
|---|---|
| «записи раздела X», «незакрытое у Олега», «что в среду» | SQL по полям. Точного фильтра вектор не даёт |
| «где было про акт сверки», «запись про кран на кухне» | **Поиск**: вектор + слова (раздел 7) |

## 2. Что индексируется

Всё, у чего есть текст, который однажды захочется найти по смыслу. Новая сущность с текстом —
новый тип в том же индексе, а не второй механизм: нарезка, эмбеддер, изоляция и реиндекс
у всех одни.

- **Тип** — значение `SearchEntityType` (`src/PetTemplate.Shared/Enums`). В шаблоне оно одно —
  `None = 0`, в индекс не попадает; разделы дописывают свои в конец (номера уезжают в тело
  команды очереди).
- **Источник** — `ISearchSource` (`src/PetTemplate.Services/Search`) на каждый тип: `Load(id)` —
  текст сущности и её пространство (`SearchDocument`), `AllIds()` — все id для реиндекса.
  Регистрация — `AddSearchSource<T>()`: знание о сущностях приходит регистрацией, а не `switch`
  по типу в обработчике, и ядро не правится. Два источника на один
  тип — обработчик падает на первой команде.
- **Текст** — заголовок первым (`# {Название}`), затем тело: по заголовку ищут не реже, чем по телу.

## 3. Эмбеддер и коллекция

**Эмбеддер свой, на процессоре.** Контейнер `embeddingscontainer` рядом с API — llama.cpp
с моделью `multilingual-e5-small` в Q8 (126 МБ весов, 384 измерения, прилично работает
с русским). Протокол — OpenAI-совместимый `POST /v1/embeddings` (адрес в настройках —
с `/v1`, клиент дописывает `embeddings`), клиент — `SearchEmbedder` за
`IEmbeddingGenerator<string, Embedding<float>>` (Microsoft.Extensions.AI): тем же
эмбеддером считает векторы справка (`help.md`, 6.3), своей модели она не заводит.
Векторы не уходят к внешнему поставщику — текст остаётся у нас. Модель мелкая из-за машины (2 ядра, 6 ГБ на всё) — что с ней не так
и куда расти, `tech-debt/embeddings-model.md`.

**Префиксы e5 — включены** (решение шаблона, `tech-debt/embeddings-model.md`). Семейство e5
обучено с парой `query: ` / `passage: `, и карточка модели велит ставить её всегда. Знак
«запрос или документ» едет в опциях вызова (`EmbeddingPurpose.ForQuery()` /
`ForPassage()`), префикс ставит `SearchEmbedder` из `SearchOptions.EmbeddingsQueryPrefix` /
`EmbeddingsPassagePrefix`; вызов без знака уходит как есть. Замер 2026-11-01 (пять записей,
девять запросов, раздел 7) разницы в порядке выдачи не показал: шкала с префиксами ниже на
0.01–0.02, порог замерен уже с ними. Модель без префиксов (bge-m3) — пустые строки в настройках,
новый порог и полный реиндекс.

**Эмбеддер не обязателен для старта.** В отличие от Qdrant (`infrastructure.md`, 6) API
поднимается и без него: индексация ждёт в очереди, поиск отвечает тем, что нашёл по словам
(раздел 7). Адрес не настроен (`SearchOptions:EmbeddingsEndpoint` пуст) — регистрируется
`NullEmbedder`, индекса нет вовсе: команды индексации выполняются впустую, векторной
половины у поиска нет. Так работают функциональные тесты, кроме тестов поиска (у них
фейковый эмбеддер и настоящий Qdrant в контейнере).

**Коллекция одна на модель, а не на сущность.** Имя привязано к модели
(`pettemplate_e5_small_384`): все типы лежат вместе и различаются полем `type`, а несравнимые
векторы разных эмбеддеров в одной коллекции заставили бы поиск тихо врать — хуже, чем падать.

- Размерность, имя модели, имя коллекции, префиксы и порог — `SearchOptions`, а не константы.
- Коллекцию заводит миграция Qdrant (`EmbeddingsCollectionMigration`, применяет
  `QdrantInitializer` на старте), а не обработчик индексации: «как устроена коллекция» —
  размерность, мера близости (косинус), payload-индексы — живёт в одном месте.
- Payload-индексы по `workspaceId`, `entityId` и `type` — вместе с коллекцией: фильтр
  без индекса на большой коллекции — полный проход.
- Существующую коллекцию миграция не трогает: у Qdrant нет `ALTER`, а размерность готовой
  коллекции не меняется. **Смена модели — новое имя коллекции и полный реиндекс**
  (раздел 5); старая коллекция остаётся лежать — удалять вручную.
- Qdrant **не бэкапится**: индекс выводится из базы, восстанавливается реиндексом
  (`IaC/DEPLOYMENT.md`, раздел 10).

**Индексируются чанки, а не сущности целиком.** У `multilingual-e5` окно 512 токенов, и всё
за окном обрезается молча — слово в третьем абзаце длинного описания не нашлось бы никогда.
`SearchChunker` режет текст по заголовкам и абзацам на куски по `SearchOptions:ChunkTokens`
(300, оценка «4 символа на токен») с перекрытием в одно предложение: заголовок всегда
начинает новый чанк, абзац длиннее чанка режется по границе символов — хвост не теряется.
Точка — чанк, что в ней лежит — раздел 10. Короткой записи одного чанка обычно хватает —
правило у всех одно.

## 4. Жизненный цикл точки

Как у всего фонового в шаблоне: сохранили сущность — команда в очередь **тем же
сохранением** (`db.Enqueue(...)`, outbox; очередь — пакет `AsuTrack.LocalQueue`
на PostgreSQL, `mail.md`, 4), обработчик считает векторы и кладёт точки в Qdrant. Команда
одна на все типы и на все случаи —
`SearchIndexCommand { EntityType, EntityId }` (фабрика `SearchIndex.Of(type, id)`), обработчик —
`SearchIndexCommandHandler`:

- **создание** — команда на индексацию; id сущности (`Guid` v7) известен до сохранения,
  поэтому сущность и команда уходят одним `SaveChanges`;
- **правка** — та же команда: старые чанки сущности удаляются по фильтру `type + entityId`,
  новые записываются. Сущность — неделимая единица индекса, обрывков прежнего текста
  не остаётся;
- **удаление** — она же: источник сущности уже не находит, и обработчик уносит её точки.
  Так же — если текста у сущности не осталось или у типа больше нет источника;
- **снос пространства** (`authorization.md`, 8; удаление аккаунта — `accounts.md`, 10) —
  забота ядра, а не раздела: `WorkspaceService.PurgeContents` той же транзакцией ставит
  `SearchPurgeWorkspaceCommand { WorkspaceId }`, и обработчик удаляет из коллекции все точки
  пространства по фильтру `workspaceId` — какие бы сущности их ни положили. В payload точки
  лежит текст чанка, и снесённое пространство не должно оставаться в индексе. Строка очереди
  уходит только с зафиксированным сносом; повтор безопасен — у пустого пространства удалять нечего.
  Исчерпала попытки — точки снесённого пространства уносит полный реиндекс (раздел 5);
- **отказ эмбеддера или Qdrant** — команда падает и повторяется очередью: через минуту,
  дальше пауза удваивается до часа (повтор по умолчанию у `AddCommandQueueWorker`, `h.Add<…>()`).
  После `CommandQueueOptions.MaxAttempts` выдач (25 — около суток) команда бросается: ошибка
  в лог, счётчик `local-command-queue-given-up`, строка остаётся в `local_queue` отложенной
  насовсем (`infrastructure.md`, 2.2). Чанк, который эмбеддер не возьмёт никогда (слишком
  плотный для окна модели, `tech-debt/embeddings-model.md`), так не ходит к нему вечно;
  эмбеддер вернул не столько векторов, сколько чанков, — тоже отказ, а не частичная запись;
- пока индекс не построен, поиск находит меньше. Отдельного состояния «индексируется»
  в интерфейсе нет.

Идентификатор точки — MD5 от `тип:id:номер чанка`, разложенный в `Guid`: повтор команды
перезаписывает те же точки. Тип в ключе нужен — у разных разделов могут быть свои счётчики.

## 5. Полный реиндекс

Нужен в двух случаях: сменилась модель эмбеддингов или правило нарезки (новая коллекция
пустая), и индекс впервые строится поверх накопленных данных — всё, что завели до подключения
раздела к поиску, само в Qdrant не попадёт. Третий — потерян том Qdrant (раздел 3).

- **Запуск — из админки:** «Сводка» → «Поиск» → «Переиндексировать»
  (`POST api/Admin/Search/Reindex`, роль `AdminManagement`, `admin.md`, 4 и 6). Реиндекс идёт
  по всем пространствам сразу — это не действие участника пространства, а уровень владельца
  инсталляции. Кнопку видит только админ с этой ролью. Кто нажал — в лог приложения
  (`admin.md`, 3.5: «всё, что меняет данные, пишет, кто это сделал»).
- **Как идёт:** ставится одна `SearchReindexCommand`; обработчик не индексирует сам, а ставит
  `SearchIndexCommand` на каждую сущность каждого источника (`ISearchSource.AllIds`). Обрыв
  стоит одной сущности, а не всего прохода; эмбеддер разбирает их с той же скоростью, что и
  обычную индексацию; «как индексируется сущность» по-прежнему живёт в одном месте. Повторное
  нажатие безвредно.
- **Сначала — сироты.** До постановки команд обработчик уносит точки, которых пообъектная
  индексация не найдёт: типа, которого нет среди зарегистрированных источников (значение
  `SearchEntityType` переименовали или убрали, раздел 10), — фильтром `must_not` по их именам
  (`QdrantService.DeleteUnknownTypes`), и пространств, которых нет в базе (команда сноса
  исчерпала попытки, раздел 4), — пространства берутся выборкой по payload-индексу
  `workspaceId` (`IndexedWorkspaces`) и сверяются с таблицей `workspaces`. Эмбеддер не
  настроен — индекс не ведётся, и чистки нет. Упала чистка — повтор команды проходит её заново.
- **Своим воркером очереди.** Команды поиска — индексация, реиндекс, снос пространства —
  разбирает отдельный воркер в один цикл, а не общий с письмами: реиндекс ставит команду
  на каждую сущность, и письмо подтверждения иначе ждало бы за тысячами чанков.
- **Ответ** значит «в очереди», а не «готово».

## 6. Изоляция пространств

**Qdrant не знает про пространства:** коллекция одна на всех, и вектор чужого пространства
лежит рядом с вашим. Забытый фильтр здесь — утечка чужого содержимого, самая дорогая
ошибка в этой фиче. Поэтому:

- payload точки **обязан** нести `workspaceId` — источник не может отдать текст без него
  (`SearchDocument.WorkspaceId`);
- фильтр по нему **обязателен** и не параметр «по желанию»: `QdrantService.Search` принимает
  `workspaceId` обязательным аргументом и подставляет фильтр сам — метода поиска без
  фильтра нет; `HybridSearch.Vector` берёт пространство из `VectorQuery`, где оно — обязательное поле;
- полнотекстовая половина фильтрует по пространству сама, своим `Where` (раздел 9);
- на это есть тесты, которые падают, если фильтр убрать
  (`SearchIndexWorker.SearchNeverLeavesItsWorkspace`, `HybridSearchNeverLeavesItsWorkspace`).

**Фильтра по пространству мало.** Индекс знает про пространство, но не про права — и не
должен. Что человеку можно видеть, решает доборка после поиска через сервис раздела и его
права (`authorization.md`, 1), а не payload точки: переписывать точки при каждой смене прав —
фоновая переиндексация, которая однажды отстанет. Плата — выдача может схлопнуться, если в лимит
попали в основном невидимые записи; лечится запросом с запасом, а не ослаблением правила.

## 7. Поиск

**Два поиска и слияние.** «Кран» в запросе и «кран» в записи вектор найдёт, но ниже, чем
ключевой поиск нашёл бы дословно; а номер договора, название контрагента и фамилию эмбеддинг
теряет почти всегда — это редкие токены без «смысла». Поэтому поиск гибридный:

- **векторная половина** (`HybridSearch.Vector`) — запрос в эмбеддер с префиксом запроса,
  ближайшие чанки из Qdrant с фильтром по пространству и типу (раздел 6) — втрое больше
  лимита, у сущности бывает несколько чанков, — выдача схлопывается по сущности: лучший
  чанк даёт ей счёт и фрагмент. Коллекции нет — пустая половина. Чанки ниже порога
  `SearchOptions.VectorMinScore` отбрасываются: без порога ближайший сосед есть всегда,
  и на посторонний запрос выдача никогда не пустая. Порог — 0.83 у `multilingual-e5-small`
  с префиксами (замер 2026-11-01: подходящие по смыслу — 0.815–0.88, посторонние — до 0.83).
  Порог замерен под модель и способ её звать и меняется вместе
  с ними;
- **полнотекстовая половина** — PostgreSQL `tsvector`
  (`infrastructure.md`, 3.1): вычисляемая колонка `GENERATED ALWAYS AS (to_tsvector(...)) STORED`
  с GIN-индексом (`FullTextSearch.HasFullTextSearch`, `src/PetTemplate.Db/Extensions`) и запрос
  `websearch_to_tsquery` «любое из слов» (`FullTextSearch.AnyWord`), порядок — `ts_rank`. Словари `russian` (`FullTextSearch.Config`): русские слова
  сводятся к основе («крана» находит «кран»), латиница — английским стеммером. Индекс один,
  без второго хранилища; ввод человека с кавычками и минусами запрос не роняет;
- **слияние по RRF** (`HybridSearch.Merge`, `Ranked`, k = 60): позиция в каждой выдаче важнее
  её абсолютного счёта, и найденное обоими способами обгоняет найденное одним. При равном
  счёте — больший ключ выше (у `Guid` v7 — новее).

**Отказ — не ошибка.** Эмбеддер или Qdrant лежат, не отвечают за 5 секунд — векторная
половина пустая, поиск отвечает тем, что нашла полнотекстовая; отказ — предупреждение в логе.
Эмбеддер не настроен — векторной половины нет вовсе.

**Пределы.** Не больше 20 результатов (`HybridSearch.MaxResults`). Запрос обрезается по краям
и до 200 символов (`HybridSearch.Normalize`); пустой — пустая выдача, а не весь список.

**API** — метод поиска заводит раздел у себя, под теми же правами, что и его список
(`GET {Раздел}/Search?q=`, `Read` или `Crud`), пространство — из `X-Workspace-Id`. Найденные
идентификаторы превращаются в DTO той же проекцией, что список: найденное выглядит так же,
как в списке. В ядре такого метода нет — нет сущности.

## 8. Экран

Экрана поиска в шаблоне нет — есть строка поиска, которую ставит раздел над своим списком.

Строка — общий `shared-search-box` (`src/app/shared/search-box`): «Найти» или Enter
отправляет запрос, а не каждая буква — каждый запрос считает вектор. Поле — до 200 символов,
как `HybridSearch.Normalize`; пока поиск идёт (вход `busy`), «Найти» неактивна. Компонент
отдаёт запрос событием `search`, а «Сбросить» (видна, пока на экране выдача; пустой запрос
поверх выдачи — то же) — событием `cleared`. Выдачу рисует экран раздела: она заменяет
список в порядке сервера, пусто — «Ничего не нашлось» (`core.empty.nothingFound`). Подписи —
в словаре `core` (`core.search.*`), потому что строку ставят разные разделы. Компонент
ни один экран шаблона не импортирует: его импортирует раздел, и в initial он не попадает.

## 9. Как подключить поиск к своей сущности

То же по шагам — в `README.md`, «Поиск: подключить к своей сущности». Образец целиком — тестовая сущность
`tests/PetTemplate.Tests/Features/Search/TestNotes` (`TestNote`, `TestNoteSource`, `TestNoteSearch`).

1. **Тип** — значение в конец `SearchEntityType`.
2. **Колонка для слов** — свойство `NpgsqlTsVector SearchVector` у сущности и
   `builder.Entity<Note>().HasFullTextSearch(x => x.SearchVector, x => new { x.Title, x.Body })`
   в модели; дальше — миграция, как у любой колонки. Колонку пишет база.
3. **Источник** — класс `ISearchSource` своего типа: `Load` отдаёт `# {Заголовок}\n\n{Тело}`
   и `WorkspaceId` сущности, `AllIds` — все id; регистрация —
   `services.AddSearchSource<NoteSearchSource>()`.
4. **Индексация** — в сервисе раздела при создании, правке и удалении
   `db.Enqueue(SearchIndex.Of(SearchEntityType.Note, note.Id))` до того же `SaveChanges`.
   При сносе пространства точки раздела уносит ядро (раздел 4) — в `WorkspaceService.PurgeContents`
   раздел удаляет только свои строки.
5. **Поиск** — сервис раздела: `HybridSearch.Normalize`, векторная половина
   `HybridSearch.Vector(new VectorQuery(workspaceId, type, query, HybridSearch.MaxResults), …)`,
   полнотекстовая — свой запрос по `SearchVector` **с фильтром по `WorkspaceId`**
   (`Matches`/`Rank` с `EF.Functions.WebSearchToTsQuery(FullTextSearch.Config, FullTextSearch.AnyWord(query))`),
   слияние — `HybridSearch.Ranked(HybridSearch.MaxResults, byVector, byWords)`.
6. **Эндпоинт** — `GET {Раздел}/Search?q=` под правами списка; доборка найденного — проекцией
   списка, которая сама фильтрует по пространству и правам (раздел 6).
7. **Экран** — `shared-search-box` над списком (раздел 8).
8. **Тесты** — изоляция пространства (свой и чужой с одинаковым текстом), правка, удаление,
   слияние — по образцу `Features/Search/SearchIndexWorker`.
9. **Первый выкат** — полный реиндекс из админки (раздел 5): записи, заведённые раньше, сами
   в индекс не попадут.

## 10. Модель данных

Своих таблиц у поиска нет: индекс выводится из сущностей разделов, и потерять его не страшно
(раздел 5).

**Точка в Qdrant** — коллекция `SearchOptions:EmbeddingsCollection` (`pettemplate_e5_small_384`),
вектор `EmbeddingsDimension` (384) с косинусной мерой; точка — один чанк одной сущности.

| Поле | Что лежит | Индекс |
|---|---|---|
| id | `Guid` из MD5 от `тип:entityId:номер чанка` (раздел 4) | — |
| вектор | эмбеддинг текста чанка с префиксом `passage: ` | — |
| `type` | **имя** значения `SearchEntityType` строкой (`Note`, а не `1`) | keyword |
| `entityId` | id сущности строкой — как его отдал источник | keyword |
| `workspaceId` | пространство сущности, `Guid` строкой (раздел 6) | keyword |
| `chunk` | номер чанка, с нуля | — |
| `text` | текст чанка без префикса — из него берётся фрагмент выдачи | — |

Тип в payload — именем, а в команде очереди — числом: переименовали значение
`SearchEntityType` — точки со старым именем фильтр больше не находит, нужен полный реиндекс.
Он же уносит старые точки — и точки убранного из перечисления типа: всё, чего нет среди
зарегистрированных источников, сирота (раздел 5).

**Колонка для слов** — у каждой сущности своя, в её таблице: `NpgsqlTsVector SearchVector`
(в базе `search_vector tsvector`), вычисляемая
`GENERATED ALWAYS AS (to_tsvector('russian', …)) STORED` по полям из `HasFullTextSearch`,
и GIN-индекс по ней. Пишет её база; в EF-модели ядра таких колонок нет — нет сущностей.

**Команды** — строки общей очереди `LocalQueue` (`mail.md`, 4): `CommandType` — устойчивое
имя команды (`[CommandType]`, `infrastructure.md`, 2.2), `Data` — JSON тела.
`SearchIndexCommand` (`search-index`) — `{"EntityType": <число>, "EntityId": "<id>"}`,
`SearchReindexCommand` (`search-reindex`) — `{}`, `SearchPurgeWorkspaceCommand`
(`search-purge-workspace`) — `{"WorkspaceId": "<id>"}`.
