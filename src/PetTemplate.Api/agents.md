# Инструкции для работы с бекендом проекта PetTemplate

## Валидация

- Используем `ModelState` с `DataAnnotations` для валидации входных данных
- Контроллеры или отдельные эндпоинты помечаются атрибутом `[ValidateRequest]`
- **НЕ нужно** в теле методов контроллера дополнительно проверять `ModelState.IsValid`
- **НЕ указываем** тексты сообщений об ошибках в атрибутах валидации (например, `ErrorMessage`), так как они отображаются на фронтенде на языке интерфейса пользователя
- Ответ `422` — `{ "поле": [ { "code", "params", "text" } ] }`, имя поля в camelCase (`ValidateRequestAttribute`).
  Свой атрибут отдаёт **код** из `PetTemplate.Shared/Errors/ValidationCodes` (с подстановками — `ValidationError.Pack`);
  встроенным (`[Required]`, `[MaxLength]`, `[Compare]`, `[Range]`) коды проставляет `ValidationCodeMessages`.
  Фраза вместо кода уезжает текстом без кода. Отказ по всей форме — поле `payload` (`ValidationFields`)
- Логин, пароль и телефон на входе — только атрибутами `[UserName]`, `[Password]`, `[PhoneNumber]`
  (`PetTemplate.Shared/Validation`, `specs/accounts.md`, 4.1 и 8.1): правила одни на регистрацию, приглашение и профиль.
  Длину логина и почты держат DTO: колонки `citext`, и база предела не держит (спец. infrastructure, 3.1)

## Аутентификация и права в пространстве

Устройство — `specs/authorization.md`, 1.2 и 2.

- Права есть только внутри пространства (workspace), глобальных `ClaimTypes.Role` нет.
  **В токене прав нет**: сервер читает их из базы на каждом запросе — отметкой `SessionGuard`
  (`PermissionsIn`, кэш 30 секунд, спец. authorization, 2.3). Активное пространство приезжает
  заголовком `X-Workspace-Id` (`HttpContextExtensions.GetWorkspaceId`, нет или не `Guid` — `400`)
- Кто меняет состав или права пространства (выдача и отзыв прав, выход, удаление участника,
  приглашение, создание, удаление и слияние аккаунта), **после коммита** зовёт
  `SessionGuard.Forget` для каждого, чьи права поменялись. До коммита нельзя: чтение между
  сбросом и коммитом положит в кэш старое. Внутри чужой транзакции — сбрасывает тот, кто её коммитит
- Эндпоинт внутри пространства помечается `[AuthorizePermissions(PermissionEnum.…)]`:
  нужно хотя бы одно из перечисленных прав **в пространстве из заголовка**. Проверка — фильтром
  авторизации, до разбора тела и `[ValidateRequest]`: посторонний получает `403`, а не `422`.
  `[AuthorizePermissions]` без аргументов — «участник пространства» (любое право в нём):
  так закрыт состав пространства, у которого своего права нет
- Без атрибута — только то, что живёт вне пространства или до него: создание, список своих,
  основное, выход (`WorkspaceController`), анонимные методы приглашения и `Accept`
  (пространство берётся из приглашения). Метод, читающий `workspaceId` из параметров без
  атрибута, — только из белого списка `WorkspaceWiringTests`: новый дописывается туда явно
- **НЕ дублируем** проверку прав внутри сервисов — она на уровне контроллера, атрибутом.
  Сервис фильтрует сущности по пространству, а id из чужого — ошибка, а не доступ
- **ВАЖНО:** Для методов чтения (GET) указываем **оба** разрешения: `Crud` и `Read`, например
  `[AuthorizePermissions(PermissionEnum.WorkspaceMemberCrud, PermissionEnum.WorkspaceMemberRead)]`:
  `Crud` подразумевает просмотр
- Сессию собирает только `AuthResultFactory`. Запрос, который сам меняет права вызывающего
  (создание пространства, выход, приглашение) или отзывает сессии (смена пароля), отвечает
  новой сессией: клиенту нужен свежий `permissionsByWorkspace` — второй вызов «за сессией»
  не заводим (спец. authorization, 2.2)
- Права разделов проекта — точка расширения: значения в конец `PermissionEnum` и его
  клиентского двойника, подпись в `permission-catalog.ts`, выдача существующим участникам
  миграцией данных (спец. authorization, 1.1)

### Пароль и сессии

- Пароль — **только через `PasswordHasher`** (`Set`, `Verify`, `NeedsRehash`): PBKDF2-SHA512, вся схема
  в строке `User.PasswordHash`. Сравнивать хеши руками, писать `PasswordHash` мимо него нельзя —
  пароль, заданный одной копией схемы, не подошёл бы ко входу другой. Хеш прежней схемы шаблона v1
  (SHA-256 с солью в `SecurityStamp`) пересчитывается при входе сам
- Отзыв сессий — `SessionGuard` (`specs/accounts.md`, 8.1): на каждом запросе `OnTokenValidated`
  (`RejectRevokedSession`) сверяет `iat` токена с `User.TokensValidAfterUtc` и проверяет, что
  аккаунт есть; та же отметка несёт права по пространствам. Кто меняет пароль (или удаляет аккаунт), ставит отметку `SessionGuard.Revoke`
  тем же сохранением, после сохранения зовёт `Forget`, а текущей сессии отдаёт новый токен
  (`AuthResultFactory.Build`) в ответе. Новый выпуск токена — только через `AuthResultFactory`
  (админский — только через `AdminTokenFactory`): в нём клейм `iat`, без него отзыв не работает
- Проверка пароля — под лимитом неудач `LoginLimiter` (`specs/accounts.md`, 8.1; общий
  со входом в админку): `TryBeginProduct(userId, ClientAddress.Key(...))` до проверки,
  `attempt.Succeeded()` после верного пароля; заперто — `400 auth.error.tooManyAttempts`.
  Так устроены `Auth/LogIn`, `Auth/LogInAndLink`, `Account/ConfirmPassword`,
  `Account/ChangePassword` и пароль второго в `Account/MergePreview`; новая проверка пароля — так же
- Профиль наружу — только `ProfileDto` через `ProfileMapping.ToDto`, никогда сущность: иначе
  со связанным `User` уедут хеш и соль
- Гонка на уникальном индексе (логин, почта) — `DbErrors.IsDuplicate(ex, DbErrors.…Index)`:
  код Postgres `23505` и имя индекса разбираются только там; проигранная гонка за замки
  (`40P01`, `55P03`) — `DbErrors.IsLockConflict`. «Пока смотрели, всё поменялось» —
  `ConflictException`, ответ `409`

### Ссылки на человека

- Аккаунт удаляется физически (`specs/accounts.md`, раздел 10) — одним путём, `AccountDeletion`
  (профиль, слияние, админка). Новая ссылка на пользователя (`User`/`Profile`)
  сразу решает, что с ней будет: авторство (кто завёл, кто пригласил) — нуллабельная колонка
  с внешним ключом `OnDelete(DeleteBehavior.SetNull)`, клиент показывает «Удалённый пользователь»;
  личное (токены, настройки) — `Cascade`. `Restrict` на пользователя не ставим: удаление аккаунта
  упадёт на нём. Личное без внешнего ключа удаляет шаг `AccountDeletion` до строки `User`
- Ссылаемся по `Id`, а не по логину: логин меняется и освобождается (4.3). Копия логина —
  только в журналах (`AccountMerge`), рядом с id
- Сущность с автором — ещё и счётчик в карточке аккаунта (`AccountCards`, спец. accounts, 7.3):
  человек видит на экранах слияния и удаления, что заведено им и что удалится

### Админка

Устройство — `specs/admin.md`, 3.3–3.5.

- Контроллеры админки — маршрут `api/Admin/...`, атрибут **`[OutsideWorkspace]`** на классе
  и **`[AuthorizeAdmin(AdminRole...)]`** на каждом методе (или классе). Без ролей
  в атрибуте — «любая роль», для экранов на чтение
- `[AuthorizePermissions]` и `[Authorize]` на них не ставим: у админки своя схема
  JWT (`AdminAuth.Scheme`), своя аудитория и свой ключ (`AdminOptions`), а пространства
  у её запросов нет. `[OutsideWorkspace]` — единственный признак «вне пространства»;
  вместе с `[AuthorizePermissions]` он роняет запрос (`PermissionsValidation`)
- Всякий отказ админского эндпоинта — `404` без тела: существование админки не
  сообщаем (`AdminNotFound` делает пустыми и `405`/`415` на админских путях).
  `[ValidateRequest]` на входе нет — его `422` выдал бы, что дверь тут есть.
  Кодов отказов (`ErrorMessage`) админка не заводит — ошибки показываются текстом как есть
- Отсюда и исключение из правила «русских строк в `throw` не бывает»: отказ по
  содержанию запроса админский сервис бросает `AdminRejectionException` с русским текстом,
  и `400` везёт его клиенту в поле `error`. Голый `ArgumentException` — это `500`. Проверки полей — в сервисе, а не атрибутами:
  у `422` валидации в теле коды, а переводить их админке нечем. «Такой записи нет» —
  голый `NotFound()` из контроллера, как и любой другой отказ админки
- Вне `[AuthorizeAdmin]` четыре метода: `Admin/Login`, `GET Admin/Invitations/{token}`,
  `Accept` и подзапрос шлюза `Admin/Auth/Verify` — он авторизуется кукой
  (`AdminAuth.GatewayScheme`), а не заголовком, и отвечает `401`: его спрашивает nginx перед
  Grafana. Куку схемы `admin` не читает — ни один админский метод по ней не открывается.
  Разметку стережёт `AdminWiringTests` — новый открытый метод дописывается туда явно;
  новый маршрут с его ролью — в `AdminRoutesApiTests.Routes`
- Админский токен выпускает только `AdminTokenFactory` (клейм `iat`, роли клеймами,
  час без продления); отзыв сессий — тот же `RejectRevokedSession`, что у продукта
- Всё, что меняет данные, пишет, кто это сделал: у выдачи роли — `GrantedByUserId`,
  у снятия — запись в лог приложения

### Сверка пространства с параметрами

- `[AuthorizePermissions]` **автоматически** сверяет пространство из заголовка с query-параметром
  `workspaceId`, параметром маршрута `workspaceId` и свойством `WorkspaceId` в DTO — фильтром
  действия раньше `[ValidateRequest]` (`AuthorizePermissions.FilterOrder`)
- **НЕ нужно** писать вручную `if (dto.WorkspaceId != workspaceIdFromHeader)` в методах
- Не совпало — `403 Forbidden`: иначе право, выданное в своём пространстве, открывало бы
  чужое, названное в параметрах

### Отказы: `422` у поля или `400`

- `422` у поля — отказ виден из самого запроса (пустой набор прав): `IValidatableObject.Validate`
  у DTO, `new ValidationResult(Messages.X.Code, [nameof(Поле)])` — в `ModelState` уезжает код,
  клиент переводит его своим словарём. Наружу он едет той же формой
  `{поле: [{code, params, text}]}`, что и коды атрибутов (`ValidationError.Parse`)
- `400` — для отказа нужна база или состояние: `throw new BadRequestException(Messages.X)`,
  где `Messages.X` — `ErrorMessage(code, text)` в `PetTemplate.Shared/Constants`. Нет сущности —
  `NotFoundException` (404). Код начинается с имени словаря клиента; `npm run i18n:codes`
  сверит, что перевод есть

## Конфигурация и секреты

- `appsettings.json` и `appsettings.Development.json` лежат в репозитории **как образец
  структуры**: какие секции и ключи читает приложение. Значения в них — заглушки
  и примеры, а не боевые данные. В `appsettings.json` строка подключения — заглушка
  под сервер (`dbcontainer`, `pettemplate_app`, `<type_password>`), рабочая для
  `dotnet run` — в `appsettings.Development.json` (`localhost:5432` из корневого
  `docker-compose.yml`)
- На сервере всё, что имеет значение, приезжает **переменными окружения** из секретов
  GitHub: строка подключения, `JwtOptions:SigningKey`, `AdminOptions:SigningKey`,
  `Telegram:BotToken`, `VkOptions:PrivateKey`, `MailOptions:Password`, `AssistantOptions:Providers:main:ApiKey`
  (`specs/infrastructure.md`, раздел 9; полный список —
  `IaC/DEPLOYMENT.md`, раздел 6). `docker run` один — `IaC/run-api.sh`: он передаёт их
  контейнеру (`--env ИМЯ` без значения), а значения берутся из `env:` шага `publish-api.yml`
  и `rollback-api.yml`. Конфигурация ASP.NET читает их поверх файла, поэтому значение
  из репозитория в прод не попадает никогда
- Это **осознанная организация кода, а не долг**: заводить в `tech-debt/`
  «секреты в `appsettings.json`» не нужно. Настоящих значений в файлах нет и быть
  не должно: новый ключ — секретом GitHub, строкой `--env` в `IaC/run-api.sh` и строкой
  в `env:` шага обоих workflow
- Адреса соседних контейнеров — не секреты, и в переменные окружения им не надо:
  они лежат в `appsettings.Release.json` (по имени контейнера из `IaC/docker-compose.yml`
  в сети `nginx-proxy-man`; первым туда встанет Qdrant — `qdrantcontainer:6334`,
  с поиском, `specs/infrastructure.md`, 6). Деплой уже ставит `ASPNETCORE_ENVIRONMENT=Release`,
  поэтому файл подхватывается сам, а значения для своей машины остаются
  в `appsettings.Development.json`

## Очередь команд и письма

Устройство — `specs/mail.md`, 4; пакет — `AsuTrack.LocalQueue` (`specs/infrastructure.md`, 2.2).

- Всё, что не должно ни теряться, ни выполняться в запросе (письмо), — **командой в очередь**:
  `db.Enqueue(command)` (`LocalQueueHandlers/CommandQueue`) до общего `SaveChanges` — команда
  ложится в `local_queue` той же транзакцией, что и доменное изменение (outbox). Отдельный
  `SaveChanges` на команду не делаем. Команда — класс с `ICommand` и атрибутом пакета
  `[CommandType("kebab-case")]` (новое имя — строкой в `QueueRegistrationTests.QueueNamesAreStable`;
  сменить имя — `[CommandType("new", "old")]`, прежнее не выбрасывать);
  тело сериализует `CommandQueue`, `ToString()` у команды не переопределяем
- Обработчик — `LocalQueue.Processing.ICommandHandler<TCommand>` пакета, регистрация —
  `h.Add<TCommand, THandler>(retryAfterFailure)` внутри `AddCommandQueueWorker(h => …)`
  в `ServicesExtensions.AddCommandQueue` (`Workers/CommandQueueRegistration`). Упала — строка
  прячется на `retryAfterFailure` (по умолчанию минута), и с каждой попыткой пауза удваивается
  до `CommandQueueOptions.MaxRetryAfterFailure` (час); после `CommandQueueOptions.MaxAttempts`
  выдач (25; свой — `h.Add<…>(maxAttempts: …)`) команда бросается с ошибкой в лог и остаётся
  в таблице отложенной — её показывает тревога «Команда очереди не проходит».
  Исключение — повтор, поэтому обработчик идемпотентен: сам проверяет, что уже сделано
  (письмо — по `AccountToken.MailSentAtUtc`)
- **Воркеры.** Обычная команда — в общий воркер (один цикл, `CommandQueueOptions`). Команда,
  которая идёт минутами или пачками и не должна ни ждать за чужими, ни держать их (ход ассистента,
  сверка модели, индексация поиска), — своим воркером: ещё один `AddCommandQueueWorker(h => h.Add<…>(), workers, prefetchCount,
  invisibilityTimeout)`. Обработчик долгой команды продлевает аренду своей строки между шагами —
  `LocalQueue.Processing.ICommandLease.Extend(срок, ct)` пакета (вне воркера — ничего не делает)
- Почта — только из обработчика очереди через `IMailSender`; тексты — `Mail/Templates/{ru,en}.json`
  на языке профиля (`Profile.Language`), никогда не на неподтверждённый адрес, кроме письма
  подтверждения. Ссылочный токен в очередь и в базу не кладём — только хеш (`AccountTokens`)

## Поиск

Устройство и рецепт подключения сущности — `specs/search.md` (раздел 9).

- Индексация — только командой: `db.Enqueue(SearchIndex.Of(тип, id))` тем же `SaveChanges`,
  что создание, правка и удаление сущности. Эмбеддер и Qdrant из запроса не зовём
- Знание о сущности — `ISearchSource` своего типа (`AddSearchSource<T>()`), а не правка
  `SearchIndexCommandHandler`: обработчик один на все типы
- В Qdrant — только через `QdrantService`: поиск без `workspaceId` там не существует, и в обход
  его `QdrantClient` не заводим. Полнотекстовая половина фильтрует по `WorkspaceId` сама —
  забытый `Where` здесь такая же утечка, как забытый фильтр в Qdrant
- Эмбеддер — `IEmbeddingGenerator<string, Embedding<float>>` со знаком
  `EmbeddingPurpose.ForQuery()` / `ForPassage()`: без него префиксы e5 не встанут
- Коллекцию заводит только миграция (`IQdrantMigration`); смена модели — новое имя коллекции
  в `SearchOptions` и полный реиндекс

## Ассистент

Устройство — `specs/assistant.md`; рецепт инструментов раздела — там же, 7.1.

- Ход собирается одним `AddAssistantRuntime()` (`Assistant/AssistantRuntime`): его же берут мир
  сверки модели и мир тестов, отличия — регистрациями поверх (`Replace`). Новый сервис хода —
  туда, а не в `AddAssistant` приложения
- Раздел проекта подключается **одной регистрацией** — `services.AddAssistantSection<T>()`,
  класс `IAssistantSection`: в `Register` — инструменты (`section.Tools<T>()`), операции плана
  (`section.Operation<T>()`) и сервисы, которые они зовут; глаголы трассы, фразы и данные сверки
  модели — его же членами (спец. assistant, 7.1). Правка `AssistantTools`, `PlanExecutor`,
  `TraceSummary` и `ModelCheckRunner` под раздел не нужна
- **Инструмент ничего не пишет.** Пишущий кладёт операцию в план (`PlanCollector.Propose`);
  пишет только `apply_plan` через обработчик операции — после согласия или по прямому поручению (5.1)
  Единственное исключение — `remember_fact` ядра (12.5): факт памяти пишется мимо плана, и защищает
  его ключ, обязанный прозвучать в реплике человека этого хода (`AssistantContext.UserText`), а у
  общего факта — ещё и текст его словами (`MemoryService.IsGrounded`); по умолчанию факт личный
- **Права — декларацией, проверяет ядро**: инструмент раздела — `AssistantTool.Create(метод, имя,
  права…)` тем же набором, что на эндпоинте раздела, каталог оборачивает его в `PermittedFunction`
  (живые права перед каждым вызовом); у операции — `Permissions`, проверяет исполнитель.
  Проверять права в теле инструмента не нужно. `userId` и пространство — только из
  `AssistantContext`, в схеме инструмента их нет
- **Данные людей — не в системный промпт** (спец. assistant, 9): имена, названия, факты, резюме
  и операции плана едут блоком данных (`AssistantPrompt.Data`, JSON в `<app_data>`); в системном —
  только наши тексты. `Instructions` раздела — текст раздела, без данных. Подстановка в шаблон —
  `SystemPromptBuilder.Fill` (один проход), не цепочка `Replace`
- Своя транзакция в коде хода и операций плана — `NestedTransaction.Begin` (`Services/Services`),
  а не `BeginTransactionAsync`: мир сверки модели ведёт ход внутри своей транзакции
- **Отказ — строкой модели**, а не исключением: инструмент ловит `NotFound`/`BadRequest`/`Conflict`
  и отвечает текстом; у операции плана — исключение, исполнитель сделает из него крестик
- Схема инструмента плоская (строки, числа, `bool`); описания — `[Description]`, по-русски; имя
  инструмента уникально во всём каталоге
- Модель — только через `IModelChatClients` по строке справочника (`AiModelCatalog.Pick`); своего
  `OpenAIClient` и `UseFunctionInvocation()` не заводим — цикл свой (15.2). Адаптер не-OpenAI
  поставщика приносит свой `IProviderErrorClassifier` — иначе размыкатель его отказов не узнает
  (16.5). Тесты — `FakeChatClient`, в сеть ни один тест не ходит
- Тексты, которые ассистент пишет от себя в ленту, — `AssistantTexts`; промпты — `Assistant/Prompts/*.md`
- Голос — только через `ITranscriptionService` (провод OpenAI-совместимый, поставщик — тот же
  `AssistantOptions.Providers`, своя только `Transcription.Model`); тесты — фейком движка или
  `HttpMessageHandler`, в сеть ни один не ходит. Расход голоса — `service_spend` вида `Transcription`
  с пространством и человеком, он идёт в лимит пространства (13.6)

## Метрики и трассы

Устройство — `specs/infrastructure.md`, 10: OpenTelemetry по OTLP, адрес — `OTEL_EXPORTER_OTLP_ENDPOINT`
(без него API ничего не шлёт — так локально и в тестах).

- Своя метрика — класс-синглтон со своим `Meter` (образец — `MailMetrics`),
  имя метра — `PetTemplate.<Раздел>`, инструменты — `pettemplate.<раздел>.<что>`; метр
  подключается `AddMeter` в `Program.cs`, иначе до коллектора он не доедет
- Метки — только с конечным набором значений (вид письма, тип команды): id пользователя
  или пространства в метке раздувает Prometheus
- Очередь команд меряется пакетом (`AddLocalCommandQueueInstrumentation()` в `Program.cs`,
  метр `LocalQueue`): новой команде метрики заводить не нужно

## Логирование и обработка ошибок

- У нас есть `GlobalExceptionHandler`, который автоматически обрабатывает все исключения
- **НЕ требуется** оборачивать код в контроллерах в дополнительные `try-catch` блоки для логирования
- Исключения из сервисов будут автоматически перехвачены и залогированы глобальным обработчиком
- Статус дают только свои исключения — наследники `DomainException` (`PetTemplate.Shared/Exceptions`):
  `BadRequestException` и `AdminRejectionException` — `400`, `NotFoundException` — `404`,
  `ConflictException` — `409`; плюс `BadHttpRequestException` — `400`. Всё остальное, включая
  `ArgumentException` и `InvalidOperationException` (их бросают библиотеки и `SingleAsync`), —
  баг: `500` с общей фразой и `traceId`, запись в лог уровнем `Error`. Отказ, задуманный
  кодом, бросаем своим типом, а не `ArgumentException`

## Сервисы

- Если ожидается, что в базе будет **одна** сущность, используем `SingleAsync()`
- Если ожидается **ноль или одна** сущность, используем `SingleOrDefaultAsync()` с последующей проверкой на `null`
- **НЕ используем** `FirstOrDefaultAsync()` с последующим выбрасыванием `InvalidOperationException` - вместо этого применяем `SingleAsync()`, который сам выбросит исключение при отсутствии или множественности результатов

## База данных (PostgreSQL)

Решения — `specs/infrastructure.md`, 3.1.

- **Уникальность.** Нарушение уникального индекса ловим по `PostgresException` с
  `SqlState == PostgresErrorCodes.UniqueViolation` (`"23505"`) и различаем
  по `ConstraintName` — имени в snake_case, как его дал `UseSnakeCaseNamingConvention`
  (`ix_profiles_user_name`, `pk_users`), а не по тексту сообщения.
  Разбор держим в одном месте — `DbErrors` (`PetTemplate.Services/Services`).
- **Регистр.** Колонки, сравниваемые без учёта регистра (логин, почта), — `citext`
  (`.HasColumnType("citext")`); в коде `ToLower()`/`ILike` для них не нужны.
- **Время.** Все `DateTime`, идущие в базу, — `DateTime.UtcNow`/`Kind = Utc`: Npgsql не пишет
  `Kind = Local` в `timestamptz` и падает.
- **Конкуренция.** Токен на всю строку — системная колонка `xmin`: свойство
  `public uint Version { get; set; }` и `builder.Property(x => x.Version).IsRowVersion();`.
  Конфликт —
  `DbUpdateConcurrencyException`. Токен по своему полю (`IsConcurrencyToken()`) тоже допустим.
- Типы — `text`, `bytea`, `jsonb`; `HasCharSet` и collation в модели нет.

## Style Guide

- **НЕ используем** суффикс `Async` в названиях своих методов - все методы по умолчанию асинхронные
- В методах контроллеров всегда прокидываем параметр `CancellationToken ct`
- В методах сервисов также прокидываем `CancellationToken ct = default`

## Соглашение о кодировании

То, чего выше нет и что код не опровергает. Код чаще читается, чем пишется.

### Имена

- Без венгерской нотации, без `_` внутри идентификаторов (кроме приватных полей), без префикса `C`
  у классов и `Ex` у «новой версии» метода
- Аббревиатуры из двух букв — заглавными (`IO`, `UI`), длиннее — как слово (`Guid`, `Xml`, `Json`)
- Не обобщённые имена (`Element`, `Node`, `Message`), а уточнённые (`FormElement`, `EventLog`)
- Булевы — с `Is`/`Has` (`IsOpen`, `HasValue`); счётчики — `…Count`; `Size` — байты, `Length` — элементы
- Методы, меняющие состояние, — с глагола действия (`BuildTree`), без пустых `Do`, `Make`, `Process`
- Интерфейс — `I…`; исключение — `…Exception`; атрибут — `…Attribute`; параметр обобщения — `T…`
  (однобуквенный `T` — только когда параметр один)
- Перечисление — в единственном числе (кроме `[Flags]`), у него есть значение для `0`
- `namespace` повторяет путь к файлу; `using` — вне `namespace`

### Классы и файлы

- Один тип — один файл с тем же именем; `IQuery` и `IQuery<T>` — допустимо в одном
- `partial` — только для расширения сгенерированного кода
- Порядок: константы, статические члены, поля, свойства (закрытые → открытые), события,
  конструкторы, методы (открытые → закрытые)
- Поля — только приватные, `_camelCase`; наружу — свойствами. Свойство не меняет значение
  между вызовами при неизменном состоянии — иначе это метод
- Класс только со статическими членами — `static`; у абстрактного — `protected` конструктор
- Явный модификатор доступа у каждого члена и типа

### Код

- Фигурные скобки — на новой строке; у `if`/`else`/`for`/`foreach`/`using` — всегда, кроме
  проверки аргумента с `throw`
- Вместо вложенных ветвлений — ранний `return`/`continue`
- Одна пустая строка между членами; не две подряд и не сразу после `{` / перед `}`
- Алиасы типов (`int`, `string`), `var` — когда тип виден справа
- Константа в сравнении справа: `if (user == null)`
- `string.Empty` вместо `""`, `string.IsNullOrEmpty` для проверки, `StringBuilder` для сборки
  в цикле, `Uri` для адресов
- Метод, возвращающий строку или коллекцию, не возвращает `null` — пустую (`Enumerable.Empty<T>()`,
  `[]`); наружу — `IReadOnlyList<T>`/`IReadOnlyCollection<T>`, а не `List<T>`;
  `IEnumerable<T>` — только для однопроходной последовательности
- Больше четырёх параметров — повод для модели
- Ошибку бросают исключением, а не возвращают `bool`/код — дальше её ловит `GlobalExceptionHandler`;
  повторный выброс — `throw;`, в лог — `ex.ToString()`, а не `Message`; базовое `Exception` не ловим
- Без магических чисел: таймауты, лимиты, размеры — константой или в `*Options`
- `as` — только с проверкой на `null` следом; `goto` — нет
- Actions контроллеров помечены `[HttpGet]`/`[HttpPost]`

### Комментарии

- По-русски, на отдельной строке перед тем, что комментируют, через `// ` с пробелом
- Объясняют «почему», а не пересказывают код; для типов и публичных методов — `///`
- Ненужный код удаляется, а не комментируется; блоки кода комментариями не выделяются
