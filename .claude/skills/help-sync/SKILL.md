# help-sync: справка по спецификациям

Справка — каталог `help/`: короткие статьи для человека о том, как работает сайт PetTemplate.
По ним отвечает ИИ-ассистент (инструмент `search_help`, `specs/assistant.md`).
Спецификации ассистент не увидит никогда; всё, что он будет знать о продукте, —
то, что ты сюда положишь. Полное описание — `specs/help.md`.

**Главный принцип: справку пишут заново, а не вырезают из спецификации.** Спецификация —
источник фактов, не текста. В статье есть только то, что в неё сознательно положили.

Skill не коммитит и не публикует: справка уходит вместе с фичей обычным ПР, на прод — с выкаткой
API (`publish-help.yml`).

## Команды

Из корня репозитория:

```
dotnet run --project tools/HelpCheck -- map                          # сверка карты со specs/*.md
dotnet run --project tools/HelpCheck -- map --init <файл>            # дописать новые разделы заготовкой todo
dotnet run --project tools/HelpCheck -- map --rehash <файл> "<раздел>"  # записать хэш после сверки статьи
dotnet run --project tools/HelpCheck -- map --rehash <файл>          # то же для всех разделов файла со статьёй
dotnet run --project tools/HelpCheck -- lint                         # правила текста статей
```

Ключи карты набирает утилита (`--init`), хэши считает утилита (`--rehash`) — руками не
пиши ни то, ни другое: опечатка в ключе — новый «пропавший» раздел.

## Шаги

1. **Что поменялось.** `git diff main -- specs/` и `HelpCheck map`: новые разделы (нет
   в карте), изменённые (хэш не совпал), пропавшие. Новая спецификация — `map --init`.
2. **Куда раздел.** Про то, что человек видит и делает, — в статью; иначе `skip`.
   Сомневаешься — `skip` и строка в отчёте: человек решит на ревью. Спецификация, где
   для человека нет ничего, — `<файл>: skip` целиком (так помечены `admin.md`,
   `infrastructure.md`, `search.md`, `help.md`, `mail.md` и оглавление `README.md`).
3. **Перепиши затронутые разделы статей с нуля** по правилам ниже. Не копируй абзацы.
4. **Только то, что работает.** Пометки «не реализовано», «дальше», «открытый вопрос» —
   в статью идёт только уже работающее. Работает ли — проверяй по коду (маршрут в
   `src/PetTemplate.Web/web/src/app/**/*.routes.ts`, кнопка в шаблоне, подпись в словаре
   `src/PetTemplate.Web/web/i18n/ru/`, эндпоинт), а не по формулировке спеки. Названия кнопок
   и страниц бери из русского словаря интерфейса — как человек их видит.
5. **До зелёного.** `map --rehash` по сверенным разделам, `lint`, `map`.
6. **Отчёт в ответ:** какие разделы куда ушли, что помечено `skip` с сомнением, какие
   формулировки стоит прочитать глазами (всё, что касается прав, удаления и слияния).

## Что можно писать и что нельзя

Одна проверка вместо списка: **в справке только то, что мы бы без колебаний выложили на
публичную страницу помощи.** Неловко увидеть фразу на сайте под своим логотипом — её нет
и в справке: ассистент перескажет её кому угодно.

| Можно | Нельзя |
|---|---|
| Что человек видит и где: страницы, кнопки, подписи | Имена классов, таблиц, полей, enum, эндпоинтов, заголовков, ключей конфигурации |
| Что происходит после действия и когда: «после выхода основным станет другое пространство» | Как это устроено внутри: очереди, транзакции, опросы, повторы |
| Правила, в которые человек упирается: кто может выгнать участника, что видно другим участникам | Механизмы защиты: подписи, проверки, лимиты попыток, сроки токенов |
| Известные ограничения, которые человек заметит сам | Инфраструктура и поставщики: серверы, базы, модели, контейнеры |
| Где посмотреть живые цифры: «сколько участников — на странице „Мои пространства“» | Сами живые цифры, которые меняются |
| — | Админка и роли админов |
| — | Чего ещё нет: «дальше», «скоро», черновые разделы, открытые вопросы |

Ещё:

- **Без тонкостей и лазеек.** Известные ограничения из `tech-debt/`, которые выдают
  устройство или дают лазейку («права появятся после перевхода»), не пишем.
- **О приватности — прямо:** «другие участники не видят», без оговорок.
- Смысловую утечку («письмо уходит через очередь и повторяется») линтер не поймает —
  её ловишь ты.
- **Название продукта в статьях не пиши:** «на сайте» понятно и так, а слово с заглавной
  внутри линтер примет за идентификатор.
- Пиши на «вы», коротко, глаголами действия: «откройте», «нажмите».

## Формат статьи

```markdown
---
title: Пространство и участники
page: /workspace/settings
---

## Как пригласить человека в пространство

Откройте страницу участников...

Как спрашивают: как пригласить коллегу; как добавить человека; где ссылка-приглашение

## Как выйти из пространства

...
```

- `title` — название статьи, первая часть «хлебных крошек» в поиске.
- `page` — необязательный маршрут приложения (только путь, без домена), куда ассистент
  отправит ссылкой. Линтер сверяет его с маршрутами клиента.
- Статья — про тему, которую человек узнаёт, а не про спецификацию: одна спека может дать
  две статьи, две спеки — одну.
- **Раздел `##` — один вопрос.** Заголовок — как человек бы спросил или назвал тему.
  Заголовки в статье не повторяются. `###` внутри можно, но ищется раздел целиком.
  Текста до первого `##` нет, `#` нет.
- **«Как спрашивают:»** — последняя строка каждого раздела: 2–5 формулировок через `;`
  живыми словами, включая разговорные. Человеку не показывается, поиску — главная
  подсказка.
- **Размер:** раздел ≤ 350 токенов (около 1 400 символов вместе с заголовком),
  статья ≤ 4 000. Не влезает — это два вопроса: дели по смыслу, а не по счётчику.
- Без кода, без ссылок, без адресов, без латинских идентификаторов, без ссылок на
  спецификации («раздел 5.3»).

## Статьи

Список — в `help/` (по файлу на тему): в ядре шаблона `home.md`, `account.md`, `workspace.md` и `assistant.md`.
Новую статью заводи, только если тема не ложится ни в одну из существующих — например,
раздел проекта, добавленный поверх шаблона.
